# Durable queue and delivery ledger

`sebastian.ledger.Ledger` owns a SQLite database and separate HMAC key in a dedicated private runtime directory. The directory is mode 0700 and both files are mode 0600/current owner. Symlinks and missing keys for existing databases are rejected. Transactions use BEGIN IMMEDIATE, synchronous FULL, rollback journals, and a process-local reentrant lock. All calls on one instance serialize across threads. Service startup must ensure there is one active consumer before calling recovery.

The database stores channel/account/conversation/thread/event IDs, event and ingress timestamps, optional provider row ID, job state, retry metadata, provider receipt IDs, and keyed text fingerprints. It never stores request bodies, reply bodies, attachment text or credentials. Callers must pass only identifiers into identifier/receipt/checkpoint fields. The key is a random 32-byte local secret, not a provider credential. SQLite failures from operations become a fixed error without SQL parameters. No queue exception needs private body context.

## API

- `JobMetadata.from_event(event, ingressed_at=None, provider_rowid=None)` constructs immutable metadata. `metadata.job_id` hashes the channel/account/conversation/thread/event identity. `Job` exposes `job_id`, `metadata`, `status`, and `retries`.
- `Ledger(path, clock=time.time, stale_after=600, lease_seconds=60, max_retries=3, echo_ttl=3600, max_pending=1000)` accepts an injectable clock. Nonterminal jobs are capped; overflow raises `RuntimeError('queue capacity reached')` without advancing the checkpoint. Completed dedup metadata remains retained until deliberate operator maintenance; the cap bounds active queue size, not total historical database size.
- `accept(metadata, checkpoint=(key, integer))` atomically inserts or returns the existing job and advances a monotonic checkpoint. Checkpoint is optional. `get_checkpoint(key)` returns an integer or None; `set_checkpoint(key, value)` never decreases a cursor.
- `claim()` expires stale queued/leased events and returns the next available leased `Job`, or None. `start(job_id)` must be called immediately before model work; it requires an unexpired lease and fresh event. `defer(job_id, delay)` only requeues leased work, up to three times. Running work cannot retry. Exhausted or stale work becomes `interrupted`.
- `recover()` is startup-only, with no other worker active. Running jobs become interrupted and never replay model/tool actions. Fresh leased jobs requeue. Stale commands become interrupted. Attempting deliveries become uncertain; pending unsent parts become abandoned because their ephemeral body cannot be reconstructed. Confirmed deliveries stay confirmed. Return value is `pending_interrupted()`.
- `discard(job_id)` retires leased, unsent events to `ignored` when source rehydration finds a deleted, nontrigger or self event. It cannot discard running work or a planned delivery.
- `reconcile(part_id, receipt)` changes uncertain to confirmed only when the caller has independently proven the exact part through provider metadata or a matching observed outgoing Messages record. It does not send anything.
- `pending_interrupted()` returns jobs awaiting a host-generated actionable failure. `get_job(id)` retrieves a job. Requeued bodies must be re-read from their authorized source by the engine; they are not present in the ledger.
- `plan(job_id, destination, text, index)` records only a keyed fingerprint and returns `Delivery(part_id, job_id, index, destination, status, receipt)`. Existing part identity and destination are immutable. Plan only for running/interrupted jobs. After partial delivery, use the next unused index for an interruption failure.
- `attempting(part_id)` durably transitions pending immediately before a network call. `confirmed(part_id, receipt)` and `uncertain(part_id)` resolve attempting state. No API retries an uncertain part. `deliveries(job_id)` returns ordered parts. `complete(job_id)` requires no pending/attempting parts and retires running/interrupted work. Complete means processing is terminal; confirmed/uncertain delivery distinctions remain separately inspectable.
- `uncertain_deliveries(limit=100)` returns at most 100 recent uncertain parts by default, bounded to the echo TTL; supported limits are 1 through 1000. It supports provider reads scoped to exact recorded destinations.
- `observe_self_reply(event)` confirms exactly one uncertain part only when own-outgoing metadata, exact destination, keyed fingerprint, and timestamp match. The observed time must be from two seconds before creation through creation plus echo TTL, and the part must still be within the current echo TTL. Ambiguous identical uncertain parts remain uncertain. An observed event ID already assigned to another part cannot be reused. Pending and attempting sends are never changed by observation. This is conservative content correlation, not a transport exactly-once guarantee. Slack observation must first verify the existing Sebastian bot identity and exact thread. If independently proven provider part metadata is available, callers can use `reconcile` instead; this ledger does not configure or register provider schemas.
- `abandon(part_id)` transitions pending to abandoned without sending; the engine can retire remaining planned parts after a send failure. Plan all response parts before sending so recovery can distinguish complete from partial responses.
- `is_self_reply(event)` requires own-outgoing metadata and exact channel/account/conversation/thread plus HMAC fingerprint within the echo TTL and the same observed timestamp window used for reconciliation. Pending, attempting, confirmed and uncertain parts match; abandoned unsent parts do not. This is loop suppression, never requester authentication. A provider's own outgoing event is still authenticated by existing adapter/policy boundaries.
- `stats()` returns only counts grouped by job and delivery states. `close()` closes the connection.

There is deliberately no exactly-once Messages claim. A send accepted by Messages followed by a crash can leave delivery uncertain. The host must not resend that part automatically. The same distinction applies to failures while confirming provider receipts.

Verify with `python3 -m unittest tests.test_ledger -v`. Fixtures cover duplicate/checkpoint atomicity, running crash recovery, lease expiry, stale commands, bounded retries/capacity, immutable partial delivery plans, uncertainty, abandoned unsent parts, self-echo scope/TTL, private modes, key continuity and absence of synthetic private text in every ledger file.
