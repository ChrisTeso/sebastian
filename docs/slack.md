# Slack channel adapter (S4)

`sebastian/slack.py` is a fresh bot adapter. No legacy implementation, account recreation, messages, invitations, or app configuration changes are part of these fixtures.

## Trusted integration

Install the official Python `slack-sdk>=3,<4` dependency in the selected service environment. `socket_client(app_token, bot_token)` creates its supported Socket Mode client and WebClient; supply the existing app's securely loaded `xapp-` and `xoxb-` authorizations. Never pass tokens to the model, repository, or ordinary logs. The existing installation remains authoritative.

Construct `SlackConfig` with verified workspace, bot user, bot ID, app ID, owner user ID, and first-start UTC cutoff. Wrap the returned client's `web_client` in `SlackAPI`, then call `inspect_identity()` before ingress or delivery. It checks exact `auth.test` workspace/user/bot IDs and `bots.info` app/user/bot IDs and returns only identity and granted scope header metadata. Missing scope headers are explicitly unavailable, not proof of no scopes. The app ID must match the existing app configuration; inbound callbacks must match both configured team and app IDs.

Register a trusted `Channel.SLACK` signer for that workspace with the S3 registry and construct `SlackAdapter`. Attach `SocketReceiver` to the authenticated SDK client. Its callback accepts an event into the trusted service queue, then the receiver acknowledges the envelope. Callback failure leaves it unacknowledged. Keep acceptance fast (Slack acknowledgment deadline); never perform model or history work in that callback. Only queued authenticated Socket payloads may enter `adapter.receive`. Do not expose receipt/signing to a tool or public HTTP route. Receiver credentials stay outside non-owner runtimes.

S5 owns persistent metadata, queue acceptance/crash handling, expired commands, bounded retry/reconnect, delivery reconciliation, and service lifecycle. SDK automatic reconnect and WebClient built-in retries are disabled. S4 duplicate suppression is process-local, keyed by provider conversation/message timestamp so message and app_mention deliveries collapse. A timestamp at or before first-start cutoff never triggers; durable restarts need the S5 checkpoint rather than resetting that cutoff on every event.

The adapter uses `conversations.info` to classify DMs, rather than channel names or asserted text. Owner DMs trigger automatically; groups and other users require case-insensitive textual `@sebastian` or exact native bot `<@ID>` mentions. Thread membership and earlier Sebastian participation never qualify on their own. Both queue ingress and worker rehydration enforce the mention requirement. Bot output, edits, deletions and nonmessage events do not trigger. New file-share messages retain provider file IDs, type, and size; attachment bodies and URLs are not persisted. S3 policy controls authority and destination; this installation uses `owner_group_replies=true` according to the approved owner-audience addendum.

History uses the same conversation and exact thread and at most ten strictly preceding messages. Thread roots qualify only for their own thread. Channel history reads newest first and stops after ten eligible predecessors; threaded history must finish bounded pagination before selecting the nearest ten. Missing permissions, provider failures and incomplete pagination fail explicitly rather than mixing context from other conversations. History retrieval supports only conversations visible to the app. No private-channel access is inferred from a public channel membership. Provider history limits can make context unavailable; S5 must report an actionable failure.

`SlackAPI.send(policy_decision.destination, final_text)` uses only the verified bot client and exact policy destination/thread, with no sender customization. It is an internal service method, not a model-authorized arbitrary-send tool. It never substitutes Chris's user token. S5 must apply final-only formatting, splitting, permission checks and delivery ledger before invoking it. All send tests use a fake transport; no live send is claimed.

## Checks and provider requirements

Run `python3 -m unittest discover -s tests -p test_slack.py -v`. Fixtures cover exact identity/scopes, owner/nonowner DMs, group textual/native mentions, thread routing and history, attachments, cross-workspace/app filtering, duplicate/self/subtype/backlog suppression, correct send parameters, and queue-before-ack order.

Read-only live probes remain the orchestrator's responsibility: existing app identity, bot scopes, app-level `connections:write`, Socket Mode/event subscription readiness, owner IDs/private DM metadata, and accessible conversation read capabilities. Expected event subscriptions include `message.im`, `message.mpim`, visible channel message events and `app_mention`; needed scopes depend on enabled conversations (`im:read`, `mpim:read`, `channels:read`, `groups:read`, corresponding history scopes, `app_mentions:read`, `chat:write`). Actual provider response is authoritative. No scope changes or token extraction are performed by this module.

Official sources consulted 2026-09-12: [Socket Mode Python SDK](https://docs.slack.dev/tools/python-slack-sdk/socket-mode/), [auth.test](https://docs.slack.dev/reference/methods/auth.test/), [conversation history](https://docs.slack.dev/reference/methods/conversations.history/), [thread replies](https://docs.slack.dev/reference/methods/conversations.replies/), and [bot message delivery](https://docs.slack.dev/reference/methods/chat.postMessage/).
